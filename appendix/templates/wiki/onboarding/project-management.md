# 项目管理守则

> 这份讲每条规矩**为什么**这么定，给人看。AI 助手照着执行的版本是仓库根目录的 `AGENTS.md`，两份冲突时以 `AGENTS.md` 为准并回来修这份。

一句话：**过程记录本身就是交付物。** 三个月后有人问「这个数字怎么测的」「当初为什么这么改」，
要能点开一条链接回答，而不是靠谁还记得。

下面每条规矩都按一个判据挑过：**不遵守它，手上的活还能不能往下推？**
能推的规矩迟早没人守，所以这里的规矩要么交给机器执行，要么卡在合并这一步上，做不到的就不设。

---

## 1. 东西放在哪

| 放什么 | 放哪 |
|---|---|
| 训练与推理的任务、bug（不管改哪个仓库） | `project-management` 仓库的 issue；代码仓库只收 PR |
| GKE on TPU 和网络的任务、bug（集群和节点层面） | `project-management-infra` 仓库的 issue。两拨人的通知、入口和模板都按仓库分，所以分成两个仓库 |
| 跨仓库的项目任务 | 按领域放上面两个仓库之一（组件代码不放这两个仓库；两个仓库的 `recipes/`、`repro/` 放各自方向的配方和复现） |
| 规矩、流程、权限的改动 | `wiki` 仓库的 issue |
| 设计文档、新人文档、规范 | 本仓库（`wiki`） |
| 进度总览 | org 的 GitHub 看板（Projects） |
| 和客户开会的纪要与 slides | 训练方向在 `project-management` 的 `meetings/`；GKE、网络方向和全体例会在 `project-management-infra` 的 `meetings/`。纪要由 Google 写，只做索引，结论仍回写 issue |

聊天里讨论出的结论，**当天回写到对应 issue**。没写进 issue 的结论等于没有。

## 2. 任务分层

```
Goal（方向，跨月）
 └─ Task（一件开发工作，一个 issue）
     └─ SubTask（最小可交付单元，自带测试，挂在 Task 下）
```

- Task 到了「一个模块」的工作量就必须拆成 SubTask
- 按月排期：看板的 Iteration 字段圈定本月要做的 Task，没圈进来的留在 backlog

## 3. 状态

看板 Status 只有 6 个：

`Triage` → `Design Pending` → `Ready to Develop` → `In Progress` ⇄ `Blocked` → `Done`

- **看板自带的自动规则全部打开**（issue 关闭 → Done、PR 合并 → Done 等）。状态靠人点一定会烂，靠规则改才准
- 认领 = 把自己设为 assignee，不另设状态
- 只建会被规则自动改、或每周真有人看的字段。用不上的字段别建，建了就会产出假数据

## 4. 两条路：小任务和大任务

| | 小任务（Size = S） | 大任务（Size = L） |
|---|---|---|
| 例子 | 改个配置、修个小 bug | 接一个新模型、改一条数据通路 |
| 设计文档 | 不需要 | 先写 RFC（见第 6 节） |
| 拆子任务 | 不拆 | 按 RFC 拆 |
| 完成 | 自己的 PR 合并 | 所有子任务关闭 |

不要把两种塞进同一条流程。流程太重，被绕过的一定是重的那条。

**Bug** 不分大小，直接进本月；P0 直接 In Progress。

## 5. PR

- **必须关联 issue**（正文写 `Closes northpeak/<issue 所在仓库>#N`）。`pr-check` 工作流检查（分支保护打开后，不通过不能合并）
- **评审现阶段不强制**：人少的起步阶段，需要别人看就请他评审，不需要就在 pr-check 通过后自己合并。人多起来、升级 Team 档后再改成「合并前至少 1 人批准」并由分支保护强制
- **每个 PR 都要有一位人类负责人**（assignee）。AI 用谁的账号，谁就是作者和负责人，不另外署名
- 正文按模板填，其中**「和原计划的偏差」一栏必填**（同样由 `pr-check` 检查）：可以写「无」，不能删。
  计划改了没回头记，三个月后 issue 上写的就是一个从没发生过的方案
- 核心目录改动超过 200 行，考虑拆成几个 PR

## 6. RFC（设计文档）

- 位置：本仓库 `docs/rfc/NNNN-标题.md`，编号取现有最大值加 1
- 模板：`docs/rfc/template.md`。**「非目标」一节必填**——写清这次明确不做什么、为什么。对内防止范围蔓延，对客户是封边界
- 流程：提 PR →（需要时）评审 → 合并 → 对应 Task 进入 Ready to Develop
- 「RFC 合并才能开发」不靠看板状态卡（状态能被人随手拖过去），靠 CI：大任务的 PR 必须引用一篇已合并的 RFC
- RFC 合并后方案又变了，回来改 RFC，并在 `docs/rfc/index.md` 更新状态

## 7. 数字怎么留证

客户最常问的是 loss 对不对得上、性能多少、精度有没有掉。规矩：

1. **每个数字都来自一次固定配置的运行**：固定 commit、固定配置文件，不接受「我本地跑出来是这样」
2. **和参考值按写死的容差比**：参考值（比如 GPU 上同一模型的 loss 曲线）和容差都放在仓库里，比对逻辑在代码里，不在某个人的判断里
3. **结果长期存档，按 run-ID 索引**：CI 运行页会过期，长期能找回的只有按 run-ID 存下来的报告
4. **报告、周报、issue 里出现的每个数字都附 run-ID**

CI 失败要分颜色：**「基础设施挂了」和「数字不对」是两回事**，不能共用一个红叉，否则红多了，真正的数字问题会被淹掉。

PR 里可以用评论命令触发验证（如 `/loss`），**跑完要把结论评论回 PR**，不能只回一条「已派发」。

## 8. fork 和上游

每个从开源项目 fork 来的仓库，在 README 第一段写明走哪种：

| 方式 | 意思 | 要定的事 |
|---|---|---|
| 直接在上游开发 | 改动直接提给上游，我们的 fork 只是中转 | 谁有上游权限 |
| 长期分叉 | 主线在我们这边 | **多久同步一次上游、谁负责**。不定就会越拖越远，之后想用上游的修复要一个个手工挑 |
| 浅 fork | 只是留个副本 | 不在上面开发 |

给第三方看的镜像，要么用流水线自动推，要么别建。手动维护的镜像一定会和主仓对不上。

## 9. 自动化的边界

- **会改变事实的动作**（改状态、指派、判完成）只用确定性规则
- **LLM 只写给人看的文字**（日报、周报、摘要、拆分建议），由人决定采不采纳

## 10. 每季度对账

把看板和仓库的数据拉一遍：哪些字段没人填、哪些规矩没人守、哪些自动化在空转。
没人用的字段和规矩，删掉，别让它们继续产出假记录。
