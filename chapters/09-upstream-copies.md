# 第 9 章 上游项目的私有副本

联合工程项目几乎总要改开源项目的代码：给框架加客户的模型，给调度组件打补丁。这些改动放在 org 里的**私有副本**里，每个副本用 `FORK.md` 写清它从哪来、怎么跟上游同步。

## 9.1 私有副本，不是 GitHub fork

GitHub 上**公开仓库的 fork 只能是公开的**。要在私有 org 里改一个公开项目，只能建一个新的私有仓库，把上游的历史推进去：

```bash
git clone --bare https://github.com/<上游>/<项目>.git
cd <项目>.git
gh repo create <org>/<项目> --private
git push --mirror https://github.com/<org>/<项目>.git
```

这样得到的仓库和上游没有 GitHub 层面的 fork 关系，所以要在仓库里写清楚它从哪来、怎么同步——这就是 `FORK.md`。

**仓库名保留上游原名**，不改名（第 2 章）。**关 Issues**，只收 PR。

## 9.2 三种跟上游的方式

每个私有副本在 `FORK.md` 第一段写明走哪种：

| 方式 | 意思 | 要定的事 |
|---|---|---|
| **直接在上游开发** | 改动直接提给上游，我们的副本只是中转 | 谁有上游权限 |
| **长期分叉** | 主线在我们这边，有自己的开发分支 | **多久同步一次上游、谁负责**。不定就会越拖越远，之后想用上游的修复要一个个手工挑 |
| **跟随副本** | 只是留个副本给客户看、偶尔打补丁 | 不在上面做大开发；跟上游自动同步 |

原项目里：

- `maxtext`（训练框架）走**长期分叉**：客户模型的改动不一定适合进上游
- 五个 GKE 组件走**跟随副本**：主要是让客户能看代码、偶尔打补丁，本仓不做开发

> 「跟随副本」是本书的叫法，不是 git 的 shallow clone（截断历史的克隆）。跟随副本保留完整历史，只是主线一直跟着上游走。

## 9.3 长期分叉：`maxtext` 的做法

### 分支

| 分支 | 内容 | 用途 |
|---|---|---|
| `main` | 上游 main + 本 org 的约定文件（`AGENTS.md`、`CLAUDE.md`、`FORK.md`、`.github` 里的模板） | 同步上游的落脚点，**不在上面直接开发** |
| `modelx` | `main` + 客户模型接入（第一代起步，以后各代也在这条线上） | **日常开发从这里拉分支，PR 合回这里** |
| `modelx-gen1` | 第一代基线快照，冻结在某个提交 | 只读，不再合 PR。`modelx` 就是从这个提交拉出来的 |
| `modelx-poc` | 原始 POC 代码 | 只读。POC 手册（`recipes/`）里的代码包、sha256 都对应这个提交，复现 POC 结果用它 |

几个设计要点：

**`main` 只是同步的落脚点。** 这样同步上游时只需要把上游 main 合进本仓 `main`（只多了约定文件，几乎不会冲突），再把开发分支 rebase 上来。

**开发分支名不带代号。** 原项目一开始开发分支名里带着模型的代数，下一代来了，要么新开分支（两条线并行维护），要么在旧代号的分支里放新一代的代码（名不副实）。
最后改成不带代号的名字，各代都在这条线上，旧分支冻结成快照。**复刻时一开始就用不带代号的名字。**

**冻结的快照分支要写清冻结在哪个提交、为什么冻结。** 手册和复现里引用的代码必须永远能找到。

**PR 合进开发分支不会自动关 issue**（不是默认分支），合并后手动关（第 7 章）。

### 同步上游

- **每两周把上游 main 合进本仓 `main` 一次**，然后把开发分支 rebase 到新的 `main` 上，跑一遍冒烟再推
- 每次同步后在 `FORK.md` 末尾的「同步记录」表加一行
- **rebase 有冲突时逐文件核对，不要整文件取一边**。原项目有一次整文件取了 ours，丢掉了上游新加的模型名白名单，是冒烟测出来的
- **通用的修复（和客户模型无关的）优先直接提给上游**，合进上游后再随同步回来

同步记录表：

```markdown
| 日期 | 上游 commit | `modelx` | CPU 冒烟 |
|---|---|---|---|
| <日期> | `0f1e2d3c4` | `9e8d7c6b5` | loss 8.4 → 8.2，`mtp_loss` 非零，`moe_bias_update_nonzero` 非零 |
```

### 冒烟：CPU 上 2 分钟，不占加速器

**推之前跑 CPU 冒烟。** 把模型缩到极小（几层、小 hidden、小词表），在 CPU 上跑 4 步：

```bash
JAX_PLATFORMS=cpu python -m maxtext.trainers.pre_train.train src/maxtext/configs/base.yml \
  run_name=modelx-cpu-smoke base_output_directory=/tmp/out model_name=modelx-smoke override_model_config=True \
  hardware=cpu skip_jax_distributed_system=True dataset_type=synthetic steps=4 per_device_batch_size=1 \
  max_target_length=128 base_emb_dim=256 base_mlp_dim=512 ... enable_checkpointing=False log_period=1
```

**通过标准写死**：4 步都完成、loss 下降、几个关键的诊断量非零（证明对应的代码路径真的走到了）。
把一次通过时的具体数值写进 `FORK.md`，下次同步对照。

**并且写清它证明不了什么**：「这只证明代码路径能跑通，不证明数值和 POC 一致。上加速器前先跑手册里的小规模冒烟，再和 POC 分支的结果对比。」

**为什么要 CPU 冒烟**：rebase 之后最常见的问题是代码路径断了（函数改名、参数没传、白名单丢了），这些在 CPU 上两分钟就能发现，不用等加速器排队。

### CI

上游的 CI 工作流通常需要上游自己的 runner（比如厂商内部的加速器机器），在私有副本里跑不了。**全部停用**，只保留不依赖特殊资源的检查（原项目是 `pr-check`，后来随 Actions 整体停用一起关了）。

## 9.4 跟随副本：GKE 组件的做法

### 分支

只有一个分支：上游默认分支 + 本 org 的约定文件。改动从它拉分支、提 PR 合回它。

### 自动同步上游

原项目的五个组件里，三个的上游在厂商内部的代码托管上（需要公司账号），另两个的上游是 GitHub 公开仓库。
内部上游的那几个，拉取只能由有访问权的厂商同事做，`FORK.md` 写的是一个**厂商一侧的定时任务**，每天跑一次：

- 上游有新提交时，把上游合进 `chore/sync-upstream-<上游 commit 前 9 位>` 分支，在同步记录表加一行，开 PR 合回默认分支。**这类 PR 用 merge commit 合并**（保留上游的提交历史）
- **同时满足三条时自动合并**，任一条不满足就留给人工审核：
  1. 本地检查通过（原项目写的是「pr-check 通过」；停用 Actions 后要改成同步任务自己跑检查）
  2. 本仓除约定文件外没有自己的改动
  3. 上游是在上次同步的基础上前进的（没有改写历史）
- 自动合并前**不在本仓编译或运行测试**（写明这一点，免得有人以为自动合并过的就是测过的）
- 上游再前进时，开新的同步 PR，**未合并的旧同步 PR 自动关闭**
- 被关闭（未合并）的同步 PR，上游前进之前不会重开
- **以下情况不推分支、不开 PR，报给维护人手动处理**：
  - 上游改了本 org 的约定文件（`AGENTS.md`、`CLAUDE.md`、`FORK.md`、`.github/`）
  - 合并有冲突
  - **新增的提交说明或代码里有厂商内部链接**（客户能看到这个仓库）

最后一条是跟随副本特有的风险：上游是内部项目，提交说明里常有内部 bug 链接、内部文档地址。自动同步必须过滤。

拉取用的凭据**只放在环境变量里，不写进 git 配置**；只取默认分支，不带上游代码评审系统的额外 ref。

手动同步按同样的步骤做，每次同步后在表里加一行。

### 组件的问题去哪提

`FORK.md` 写明：**组件的问题提到 `<org>/project-management-infra`**；PR 正文写 `Closes <org>/project-management-infra#<号>`。
和本 org 无关的通用修复优先提给上游。

## 9.5 导入上游代码时：不放空仓库

原项目一次性导入了一批内部组件仓库，结果有几个在内部是空的（只有一个初始提交）。规则：

- **有公开版本的，导入公开版本**
- **公开版没有、内部也是空的，不建**。org 里不放空的仓库：客户点进去什么都没有，只会困惑

导入前确认客户已经被授权看这些代码。

## 9.6 给客户模型打的临时补丁

上游的 bug 修复还没发布、客户等不及时，补丁打在私有副本的开发分支上：

- issue 里写清补丁在哪个分支、哪个提交、修的是上游哪个问题（贴上游 issue / PR 链接）
- 上游发布修复后，随同步回来，删掉补丁
- 补丁也走 PR，正文 `Refs` 那个 issue

## 9.7 给第三方看的镜像

**要么用流水线自动推，要么别建。** 手动维护的镜像一定会和主仓对不上。

## 9.8 `FORK.md` 模板

```markdown
# <org>/<项目>

这是 [<上游>](<上游 URL>) 在本 org 里的私有副本（不是 GitHub fork：GitHub 上公开仓库的 fork 只能是公开的）。

## 跟上游的方式：<长期分叉 | 跟随副本 | 直接在上游开发>

<为什么选这种；同步频率；谁负责>

## 分支

| 分支 | 内容 | 用途 |
|---|---|---|

## 同步上游

<步骤；冲突怎么处理；自动同步的条件>

## 冒烟

<命令；通过标准；它证明不了什么>

## CI

<哪些停用、哪些保留>

## 同步记录

```
