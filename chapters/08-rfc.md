# 第 8 章 RFC：大任务和规则变更

RFC（Request for Comments）是设计文档。这套做法里它有两个用途：**大任务开工前定方案**，**规则本身要改时定方案**。
两种用同一个模板、同一个流程。

## 8.1 什么时候必须写 RFC

| 情况 | 要不要 RFC |
|---|---|
| `size/L` 的任务：接新模型、改数据通路、跨模块改动、别人需要先认可方案的 | **必须**，合并后才能开发 |
| 改规则：动到已有 issue、仓库、权限的大改动（拆仓库、并仓库、改可见性） | **必须**。小改动（补一条规矩、改措辞、加一个下拉选项）走 `wiki` issue + PR 就行——原项目纳管新领域、停用 Actions 都是这样改的 |
| `size/S` 的任务 | 不需要 |
| Bug | `size/S` 的直接修；`size/L` 的（要动几个模块、别人要先认可方案）照样先写 RFC |

**RFC 合并之前只能写 RFC，不能写实现。** AI 助手的规则第 0 节第 3 条：大任务先确认 RFC 已合并。

## 8.2 放在哪、叫什么

- 位置：`wiki/docs/rfc/NNNN-<英文简述>.md`（本书的建议，理由见下）
- **编号 = 现有最大编号 + 1**。编号可能有空缺（比如有 RFC 被撤回），取最大值 + 1，**不是数文件个数**
- 在 `docs/rfc/index.md` 末尾加一行，状态 `draft`

为什么项目的技术 RFC 也放 `wiki` 而不放 issue 仓：RFC 是长期有效的设计文档，issue 仓里是一条条事务。
原项目的规则写的是「复制 wiki 的模板到**当前仓库**的 `docs/rfc/`」，结果 infra 仓有了自己的一套 `docs/rfc/`，编号从 0001 重新开始，和 wiki 的 RFC-0001 撞号，引用时还要说清是哪个仓库的。复刻时统一放 `wiki`，只有一套编号。
放在一起，所有设计决策在一个目录里按编号排好，新人从头读一遍就知道项目怎么走到今天的。

`index.md` 的格式：

```markdown
# RFC 索引

| 编号 | 标题 | 状态 | 作者 | 日期 |
|---|---|---|---|---|
| [0001](0001-infra-issue-repo-and-meeting-records.md) | 拆出基础设施 issue 仓库，约定会议纪要与 slides 的存放 | accepted | alice-g | 2026-04-02 |
| [0002](0002-merge-deliverables-into-issue-repos.md) | 配方、复现、文档、纪要并进两个 issue 仓库 | implemented | alice-g | 2026-04-03 |
| [0003](0003-numerics-check-catalog.md) | 数值对齐框架——检查项目录 | accepted | bob-g | 2026-04-08 |

新 RFC：复制 `template.md` 为 `NNNN-标题.md`（编号 = 现有最大值 + 1），在上表追加一行，提 PR。
状态变了回来改这张表。
```

## 8.3 模板

```markdown
---
title: "RFC-NNNN: 标题"
status: draft   # draft | review | accepted | rejected | superseded | implemented
author: github-用户名
date: YYYY-MM-DD
issue: owner/repo#N
---

# RFC-NNNN: 标题

## 概述
一两句话：做什么、为什么值得做。只读这一节也能明白。

## 背景与动机
现在有什么问题，不解决会怎样。

### 目标
可验证的目标，验收时逐条对照。

### 非目标（必填）
这次明确不做什么，为什么。

## 方案
期望的结果、怎么衡量成功。

### 备选方案
考虑过但没选的方案，各一句话说清为什么没选。

## 设计细节
数据结构、接口、关键流程。凡是「怎么实现」可能有歧义的地方，在这里说死。

### 测试与验证
怎么证明它对：单测、端到端、和参考值的比对（附参考值来源和容差）。

## 影响范围
影响哪些仓库、哪些人；有没有兼容性或迁移问题。

## 实施计划
分几步、每步交付什么。

## 风险
可能出什么问题，怎么应对。

## 和原计划的偏差
（实施后回填。没有偏差写「无」。）
```

## 8.4 模板里每一节怎么写好

**概述**：只读这一节的人也要明白做什么、为什么。很多人只读这一节。

**目标：可验证。** 每条目标都要能在验收时打勾。原项目 RFC-0001 的目标写法：

> 3. 四个团队在 `project-management-infra` 上的权限与 `project-management` 相同。用 API 查 `orgs/<org>/teams/<团队>/repos` 核对。
> 5. `project-management` 删除 `area/gke`、`area/network` 两个标签，删除前用这两个标签的 issue 数为 0。

不要写「提升协作效率」这种不能验证的目标。

**非目标（必填）**：写清这次明确**不做**什么、为什么。**对内防止范围蔓延，对客户是封边界。**
原项目 RFC-0001 的非目标里有一条：「升级 GitHub Team 档：维持免费档」。写下来之后，实施中有人提「要不顺便升级一下」，直接指向这条就行。

**备选方案：每个一句话说清为什么没选。** 这一节是给三个月后的人看的——他们会问「为什么不用标签区分，非要拆仓库？」，答案在这里。

**设计细节：凡是有歧义的地方说死。** 比如具体的设置值、文件内容、命令。RFC-0001 的设计细节里直接写出了新仓库每个 issue 模板的字段、`config.yml` 的全文、要删哪 7 个标签。

**测试与验证：逐条对应目标**，每条给出验证命令。

**实施计划：表格，带「权限」和「回退」两列。**

| 步 | 做什么 | 权限 | 回退 |
|---|---|---|---|
| 1 | 建新仓库，按设计设置、授权 | Owner | 归档仓库（不删除） |
| 2 | 复制并删减标签 | Maintain | 删掉新标签 |
| 7 | 删除旧仓库的两个标签；核目标 5 | Maintain | 重建标签（删除后已关闭 issue 上的标签不能恢复，所以先核为 0 再删） |

「权限」列让执行人一眼看出哪步需要 Owner 出手；「回退」列逼着写的人想清楚每一步怎么撤。
还要写清**哪些步骤必须连续做完**：「1–7 一次做完，中间不留『新仓库已建、规矩还没改』的状态超过一天」。

**风险：表格，风险 + 应对。** 引用外部证据时写出处（GitHub 文档、社区帖编号）。查不到官方说法的，明说「文档没写」，然后写防御措施。

## 8.5 流程

```
在 wiki 建 issue（或 issue 仓里已有的大任务 issue）
  → 认领，看板设 Design Pending
  → 写 RFC，提 PR（正文 Refs 那个 issue），index 里状态 draft
  → （需要时）评审
  → 合并，index 状态改 accepted
  → 对应 issue 看板设 Ready to Develop
  → 开发、实施
  → 实施完回填「和原计划的偏差」，状态改 implemented
```

RFC 的 PR 正文写 **`Refs`**，不写 `Closes`：RFC 合并只是方案定了，issue 要等实施完才关。

`wiki/.github/CODEOWNERS` 让 RFC 目录对客户开放评审：

```
*            @northpeak/maintainers
/docs/rfc/   @northpeak/googlers @northpeak/customer
```

客户可以写 RFC、评审 RFC。设计是双方的事。

## 8.6 实施后：回填偏差

**实施后方案变了，回来改 RFC，并更新 index 里的状态。**

「和原计划的偏差」一节在实施后回填，格式：日期、谁决定的、改了什么、为什么、连带改了哪些地方。原项目 RFC-0001 的偏差节：

> - **两个 issue 仓库按子团队隔开可见性**（第 14 天，项目负责人决定）：`customer` 不再对两个 issue 仓授权……推翻了「非目标」里「隔开的是入口和通知，不是可见性」一条。随之改了三处规矩：……
> - **同日改为不对称**（项目负责人决定）：`training` 也对 `project-management-infra` 授权……
> - **RFC-0002 改了四处**（第 14 天）：……

注意几个细节：

- **写「谁决定的」**：「项目负责人决定」「评审时定」。偏差不是执行人自作主张
- **推翻了原文的哪一条要点名**：「推翻了『非目标』里……一条」
- **偏差也可能被后来的偏差推翻**：用删除线划掉旧的，后面写「（同日改，见下一条）」

## 8.7 一篇 RFC 改了另一篇：删除线 + 指针

后一篇 RFC 改掉了前一篇的某些内容时，**在前一篇里原地划掉，指向后一篇**：

```markdown
和客户开会的纪要与 slides ~~统一放 `library/meetings/`~~（RFC-0002 改为训练方向放
`project-management/meetings/`，GKE、网络和全体例会放 `project-management-infra/meetings/`），纪要由厂商写。
```

```markdown
| ~~`customer`（子团队继承）~~ `gke`、`network`、`training`（2026-04-03 改，见「和原计划的偏差」） | ~~Triage~~ Write（RFC-0002） |
```

**为什么不直接改原文**：直接改原文，就看不出当时的方案是什么了；整篇标 superseded，又会让人以为整篇作废。
删除线保留了历史，指针告诉读者最新的在哪。

## 8.8 规则变更的完整链路

规则本身要改时（比如加一个标签、改转移规则、加一个仓库）：

1. **在 `wiki` 开 issue**，说明要改什么、为什么
2. 小改动（措辞、补一条遗漏）：直接提 PR 改 `AGENTS.md` 和守则，`Closes` 那个 issue
3. 大改动：写 RFC（本章流程），合并后按实施计划执行
4. `AGENTS.md` 合并进 `wiki` 的 `main` 后，**跑 `sync-agents.sh <wiki issue>`** 同步到所有仓库（第 13、14 章）
5. 守则（给人看的那份）、入职文档、org 主页一起改
6. 需要的话在例会上通知客户

**规则改动最容易漏的是第 4、5 步**：`wiki` 改了，各仓库的 `AGENTS.md` 还是旧的，AI 助手照旧的执行。
所以 RFC 的「设计细节」里要列出所有要改的文件（原项目 RFC-0001 列了一张「wiki 的改动」表，逐个文件写改什么）。

## 8.9 一个想法：用检查卡住「RFC 合并才能开发」

原项目的守则里写着：「RFC 合并才能开发」不靠看板状态卡（状态能被人随手拖过去），靠 CI：大任务的 PR 必须引用一篇已合并的 RFC。
这条在原项目里**没有真正实现**（Actions 后来停用了）。复刻时如果你有 CI，可以实现它：
PR 关联的 issue 带 `size/L` 时，检查 PR 正文里有没有 `docs/rfc/NNNN-` 的引用，且该文件在 `wiki` 的 `main` 上存在。
