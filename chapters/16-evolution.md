# 第 16 章 规则怎么演进：几次真实改版

前面各章写的是「现在的规则」，下面是它们怎么改到今天这样的。
看这些改版能知道两件事：**哪些地方一开始就该做对，哪些地方可以先简单、出了问题再改。**

时间线（原项目，按建 org 那天算第 1 天，取自 `wiki` 里 `AGENTS.md` 的提交记录，仓库名换成本书的叫法）：

| 时间 | 改了什么 | 怎么改的 |
|---|---|---|
| 第 1 天 | **建 org，第一天就提交了二十多次规则修改**（16.4） | 直接改 |
| 第 6 天 | 评论规矩加「不写分派和流程」的逐项列举；代码仓开发分支去掉代号 | PR |
| 第 7 天 | `AGENTS.md` 写明客户的代码和材料放哪 | PR |
| 第 9 天 | 纳管 GKE on TPU 和网络 | `wiki` issue |
| 第 13 天 | **拆出基础设施 issue 仓** | RFC-0001 |
| 第 14 天 | **客户可见性：先对称隔离，同日改为不对称** | RFC-0001 偏差 |
| 第 14–15 天 | **交付物仓库并进两个 issue 仓，三个旧仓库归档**；标签表加 `P1`、`P2` | RFC-0002 |
| 第 2–4 周 | Owner 从 2 人加到 5 人 | 按需 |
| 第 20 天 | 加固定路由 | PR |
| 第 21 天 | **整个 org 停用 GitHub Actions** | 改设置 + PR |

## 16.1 改版一：拆出基础设施 issue 仓（RFC-0001）

### 起因

org 建好一周后，客户的 GKE 组和网络组加入。当时的做法是：GKE、网络的 issue 也提在唯一的 `project-management`，按 `area/gke`、`area/network` 标签区分。

四天后就发现三个问题（第 2 章 2.3）：标签分不开通知、建 issue 时分不开（规矩要求建时不打 `area/*`，截至当时 16 个 issue 里只有 1 个打了 `area/gke`，另一个明显是 GKE 问题的没打）、一套模板两拨人用。

### 决定

新建 `project-management-infra`，GKE 和网络的 issue 移过去；全局进度靠 org 看板汇总，加两个按仓库筛选的视图。

### 值得学的做法

**RFC 写得极具体。** 新仓库的设置、每个模板的字段、`config.yml` 全文、要删的 7 个标签名、`wiki` 里要改的 6 个文件、14 处改动逐个列出、实施计划 13 步每步的权限和回退。实施的人照着做就行。

**非目标写得很满**：org 配置写成代码、升级付费档、问答移到 Discussions、按组件建标签、组件仓开 issue、改上游同步方式、改看板字段——全部明确「这次不做」。每一条都是实施中可能有人提「顺便做了吧」的。

**迁移前记录状态，迁移后核对**：要转移的两条 issue，一条转移前记下看板字段（Status=Triage、Size=S），另一条原本不在看板上、转移后补加，因为 GitHub 文档没写看板条目会不会随转移保留。

**删标签前先确认用量为 0**：删除后已关闭 issue 上的标签不能恢复。

**规定哪些步骤必须连续做完**：「1–7 一次做完，中间不留『新仓库已建、规矩还没改』的状态超过一天」。

### 教训

**按受众分仓库这件事，一开始就该想。** 原项目是在第二拨受众进来之后才拆的，好在只有两条 issue 要转移。
复刻时，如果你在第 0 步就知道会有两拨受众，直接建两个 issue 仓。

## 16.2 改版二：可见性从对称改为不对称（同一天改了两次）

### 第一次：对称隔离

RFC-0001 的原计划里写着一条非目标：「给客户子团队单独授权：不做。三个子团队都能看、能提两边的 issue。**隔开的是入口和通知，不是可见性。**」

实施第二天，项目负责人决定**按子团队隔开可见性**：`customer` 父团队不再对两个 issue 仓授权，训练组只看训练仓，GKE 组和网络组只看 infra 仓。理由：GKE 组、网络组的工作用不到训练方向的问题和数据，按最小权限只给需要的。

随之改了三处规矩：

- 客户提的 issue 放错了仓库**不再转移**（转过去报告人看不到），改为另一边新开一条互链
- 同时做训练和 GKE 的客户可以同时进两个子团队
- 两边 `config.yml` 互指的链接，对看不到另一边的人是 404，链接说明里写明「打不开就在本仓库提」

### 第二次：同日改为不对称

同一天又改了，从改法看，要解决的是：训练组跑作业时会碰到集群层面的问题（切片起不来、节点坏了），对称隔离后他们没法在 infra 仓提 issue、看结论。

于是改为**不对称**：训练组也能看 infra 仓；GKE 组和网络组仍只看 infra 仓。规矩随之再改：

- 转移规则按方向分：训练 → infra 可以转（训练组两边都能看）；infra → 训练仍然不转，另开一条互链
- 同时做训练和 GKE 的客户**只进 `training`**（`training` 两边都能看，已经覆盖），加人模板的团队改回单选
- infra 仓的 `config.yml` 去掉指向训练仓的链接（GKE 组打不开）

### 值得学的做法

**两次改动都记在 RFC-0001 的「和原计划的偏差」一节**，第一次的内容用删除线划掉、指向第二次。RFC 正文里被推翻的那条非目标也用删除线划掉，写明「已改为按子团队隔开可见性，见『和原计划的偏差』」。
今天读这篇 RFC 的人，能看到完整的决策过程。

### 教训

**先画可见性矩阵：每个客户组 × 每个仓库，看不看得到。** 画的时候问：这个组会不会碰到另一个方向的问题？会的话，他需要能提 issue。
原项目如果一开始就画了这张表，就不会有那个对称隔离的半天。

可见性一旦不对称，**转移规则、加人规则、`config.yml` 链接、共享内容放哪**都要跟着变。改可见性时把这四样一起检查。

## 16.3 改版三：交付物仓库并进 issue 仓（RFC-0002）

### 起因

可见性改成按子团队隔开之后，`library`、`recipes`、`repro` 三个仓库对所有客户可见，和新的边界不一致：GKE 组能看到训练方向的复现和配方。

### 决定

三个仓库按内容类型分；要按受众对齐，要么每个按方向拆两份（六个仓库），要么并进已经按受众划好的两个 issue 仓。选了后者：自有仓库从 5 个减到 2 个，GKE 组只需要关注一个仓库。

每个 issue 仓下建 `library/`、`meetings/`、`recipes/`、`repro/`。客户子团队在 issue 仓上从 Triage 改为 Write（要能维护 `recipes/`、`repro/`）。

分两阶段：第一阶段只做 infra 仓（那边当时内容少），训练仓第二阶段另行审批。实际上第二天就做了第二阶段，没有另写 RFC，在 RFC-0002 的非目标那一条后面补了一句说明。

### 值得学的做法：带历史迁移

把 `library` 仓库里的两个目录连同提交历史迁进 infra 仓：

```bash
# 在 library 的一份新克隆上
git filter-repo --path tpu-cluster-handbook/ --path gke/ \
  --path-rename tpu-cluster-handbook/:library/tpu-cluster-handbook/ \
  --path-rename gke/:library/gke/ \
  --preserve-commit-hashes \
  --message-callback '<把提交信息里的裸 #N 改成 <org>/library#N>'
# 在 infra 仓的分支上
git pull --allow-unrelated-histories <过滤后的克隆> main
# 提 PR，必须用 merge commit 合并
```

几个细节：

- **`--message-callback` 改写裸编号**：旧仓库提交信息里的 `(#5)` 指的是旧仓库的 PR #5。这些提交进了 infra 的默认分支后，GitHub 会按 infra 的编号解析，在 infra 不相干的 #5 时间线上留下引用。所以改写成 `<org>/library#5`。其他裸编号逐条判断
- **`--preserve-commit-hashes`**：不加时，`filter-repo` 会把提交信息里引用的旧提交哈希换成重写后的新哈希，迁过来的提交信息就和原仓库对不上。加了之后，代价是这些哈希在新仓库里查不到，要回旧仓库查
- **PR 必须用 merge commit 合并**：squash 或 rebase 会把迁来的历史压掉。合并前在仓库设置里临时关掉 squash 和 rebase，合并后恢复
- **验证**：迁移前后逐文件 sha256 清单一致；`git log --format="%an %ad %s"` 逐行一致（哈希会变，不比哈希），提交数相同。改写过的编号单独说明
- **链接检查要有阴性对照**：写脚本检查迁移后所有相对链接指向的文件存在；先在副本里故意改坏一条，确认脚本报错，再跑真目录

### 值得学的做法：旧仓库归档而不删除

三个旧仓库**归档**（只读）。issue 评论里有大量指向旧仓库的 commit permalink，删了就全断了。归档后它们照常能打开。
新位置的 README 里写一句来历：「本目录 <日期> 从 `<org>/repro` 仓库连同提交历史迁来。旧仓库已归档，issue 评论里指向旧仓库的 commit permalink 照常能打开。」

### 值得学的做法：明确接受的风险

免费档私有仓库没有分支保护，客户有了 Write 之后可以直接推 `main`，误操作（强推）可能改写历史。RFC 原计划由厂商定期备份仓库，实施时决定不做，并写明：
「残余风险已接受：被覆盖的提交超出 events 记录范围、又没有成员的本地克隆留着时，找不回。」

**不做的事写清楚为什么不做、接受了什么风险**，比假装风险不存在好。

### 教训

**一开始就按受众建仓库，交付物目录放进 issue 仓。** 这样就不会有这次迁移。本书第 2 章的结构就是这次改版后的结果。

## 16.4 较小的改动

### 第一天的二十多次修改

建 org 当天，`AGENTS.md` 提交了二十多次。从提交标题能看出第一版规则哪里没想清楚：

| 提交 | 说明什么 |
|---|---|
| 「AI 助手用人的账号并**强制署名**」→ 同日「**去掉 AI 署名规则**」 | 一开始要求 AI 署名，同日去掉。提交说明写的理由是「署名是冗余信息；作者以 GitHub 账号记录为准」（第 1 章原则 5 是本书展开的理由） |
| 「撤掉按阶段开的总表，默认平铺」「写明什么时候才开总表」 | 第一版允许阶段总表（`tracker` 标签的描述至今还留着「阶段总表或大任务总表」）。改为默认平铺，只在两种情况开（第 6 章 6.11） |
| 「`projects` 仓库改名为 `project-management`」 | issue 仓原来叫 `projects`（和 GitHub 的 Projects 看板同名） |
| 「规矩和权限类 issue 放 wiki，projects 只放项目」 | 一开始两类 issue 混在一起 |
| 「项目 issue 只建在 project-management，代码仓库只收 PR」 | 一开始代码仓也开 issue |
| 「projects 仓库不走 PR，直接推」 | 记录类改动的例外 |
| 「写明合进非默认分支的 PR 要手动关 issue」「改 PR 正文用 REST，不用 gh pr edit」 | GitHub 的两个反直觉行为，第一天就写进了规则 |
| 「现阶段评审不强制，可自己合并」 | 一开始要求评审 |
| 「AGENTS.md 写明命令行怎么按模板建 issue」「补下拉字段选项」「下拉选项逐个加反引号，避免和选项里的斜杠混淆」 | AI 建的 issue 和网页上的对不上，一步步把枚举写全 |
| 「类型标签加 accuracy、perf、question」「加 type/design」「加领域标签 area/*」 | 标签表逐步补全 |
| 「客户 issue 缺的信息由我们补」 | 一开始要求客户补填 |

这些改动都是在**真的用起来之后**发现的。第一版规则不可能完美，**重要的是改起来便宜**：规则在 `wiki` 里，改一次是一个 PR，`sync-agents.sh` 一条命令分发。

### 开发分支去掉代号

分支名里带着模型代数，下一代来了没处放，改成不带代号的名字（见第 9 章 9.3）。

### Owner 从 2 人加到 5 人

原规矩是「Owner 限 2 人以内」，后来发现 `maintainers` 的人加不了新成员，放宽了（来龙去脉见第 3 章 3.2）。

### 评论里不写分派和流程

规矩原来只写了「评论只写事实和结论，不写过程寒暄」。但评论里照样出现「已分给某某跟进」「已打标签」这类话——写的人（多半是 AI 助手）显然不认为这是寒暄。
于是在第 6 节单独加一条，把这类话**逐个列出来**（第 13 章 13.5）。**能列举的就列举。**

### 固定路由

某一类 issue（需要上游框架团队跟进的）每次都要分给同一个对接人，分诊的人常常不知道该给谁。写成固定路由，进了 `AGENTS.md` 第 2 节。

### 停用 GitHub Actions

一个月用完了 2,000 分钟的免费额度，失败通知也在打扰人（第 14 章 14.3）。停用后把检查改成本地脚本，`AGENTS.md` 写明「没有 CI，推前自查」。

### 客户的材料：越改越少

`AGENTS.md` 里写给客户的那段（代码放哪、材料放哪）改了好几轮，方向都是**删**：删掉「分支名要这样起」、删掉「目录里要写 README」、删掉「描述可有可无」这种多余的话。
最后剩下：「从开发分支拉一个自己的分支，改完推上去即可。分支名不做规定，不要求提 PR」「放不进 issue 的东西放 `repro/issues/<号>-<简述>/`；issue 里能写清楚的就不建目录」。

## 16.5 改规则的通用经验

1. **小改直接改，大改写 RFC。** 判据：会不会影响已有的 issue、仓库、权限。影响就写 RFC
2. **改规则必须同时改四处**：`AGENTS.md`（然后同步）、守则文档、入职文档、org 主页。漏一处，人和 AI 就会按旧的做
3. **改了的规则在 RFC 里留痕**：删除线 + 指针，写日期、写谁决定的
4. **转移、迁移前记录状态，迁移后核对**
5. **能归档就不删**：永久链接比整洁重要
6. **规则越改越短是好事**
