# 第 13 章 AGENTS.md：写给 AI 助手的规则

前面十二章的规则，给人看的版本是守则文档，给 AI 助手看的版本是 `AGENTS.md`：命令式、带命令、枚举写全。
完整模板见 [`appendix/templates/AGENTS.md`](../appendix/templates/AGENTS.md)，填空说明见[附录 A](../appendix/A-AGENTS.md)。

## 13.1 为什么规则主要写给 AI

原项目 `wiki` 的 README 第一段就写着：**「这里的规矩主要写给 AI 编码助手：它们照着写 issue、PR、打标签、改看板，项目才管得利索。」**

背后的观察：

- 工程师一天写的 issue、PR、评论，很多是让 AI 助手代写的
- **AI 照字面执行**。规则写清楚了，它每次都对；人会「差不多就行」
- 规则写给 AI 会逼着规则写具体。「PR 要写清楚」对 AI 没用；「按模板填四栏，偏差栏没有写『无』，不许删」才有用
- 人只要对助手说一句：**「先读 AGENTS.md，再按里面的规矩来」**

所以 org 主页、每个仓库的 README 都有一节「给 AI 编码助手」，告诉人类用户这句话。

## 13.2 文件的位置和读取方式

| 工具 | 读什么 |
|---|---|
| Codex、Antigravity 等 | 仓库根目录的 `AGENTS.md` |
| Gemini CLI | 默认读 `GEMINI.md`（Gemini CLI 文档 gemini-md.md）。放一个一行 `@AGENTS.md` 的 `GEMINI.md`（它支持同样的 `@` 引用），或在 `settings.json` 里设 `"context": {"fileName": ["AGENTS.md"]}` |
| Claude Code | 仓库根目录的 `CLAUDE.md`，内容只有一行 `@AGENTS.md`（`@` 语法引用另一个文件） |

**每个仓库根目录都放一份**，内容和 `wiki/AGENTS.md` 逐字节相同。AI 助手只读当前工作目录里的文件，客户在 `maxtext` 里开助手，看不到 `wiki`。

**权威版本在 `wiki`**。其他仓库的副本**不手改**，由 `sync-agents.sh` 同步（13.6）。

## 13.3 写法：五条

### 1. 命令式，照做，不要自行变通

开头第二段：

> 规则是**命令式**的：照做，不要自行变通。规则和人类同事的口头指示冲突时，以人类指示为准，并把指示写进 issue 留痕。

「以人类指示为准」给了出口：规则不可能覆盖所有情况，账号主人说了不一样的，听人的。但要留痕。

### 2. 只写怎么做，不写为什么

> 背景和理由见 `docs/onboarding/project-management.md`。这份文件只写**怎么做**。

为什么在守则里。`AGENTS.md` 每多一段解释，AI 就多一段可能误读的文字，上下文也更长。
（例外：一句话能说清、且能防止 AI 自作聪明的原因，可以括号带上。比如「不要用 `gh pr edit`（它要求令牌有 `read:org` 权限，通常没有）」——没有这个括号，AI 遇到报错会去想办法加权限。）

### 3. 枚举值写全，不让 AI 编

下拉框的每个选项、每个标签名、每个看板状态名，**逐字写出来**，放在反引号里。规则写「下拉字段只能填下面的选项之一（每个反引号里是一个完整选项），不要自己编」。

AI 最常见的错误是编一个「看起来合理」的值：标签 `type/enhancement`、状态 `In Review`、模板字段「复现步骤」。把枚举值写全就杜绝了。

### 4. 带可以直接执行的命令

不写「把 issue 加进看板」，写：

```bash
gh api repos/northpeak/wiki/contents/scripts/board.sh --jq .content | base64 -d | bash -s -- add <issue URL> S
```

命令里用到的 ID、仓库名、路径都写死。AI 不需要去查看板 id，也不需要 clone `wiki`。

### 5. 表格化

「什么情况 → 做什么」的规则用表格。模板表：模板名 / 什么时候用 / type 标签 / 正文小标题。看板状态表：状态 / 谁来改。AI 读表格比读段落准。

### 第 8 节「绝对不要」是底线

```markdown
## 8. 绝对不要

- 新建、改名、删除标签
- 建公开仓库（建仓库一律选 Private）
- 改 org 或仓库的设置、权限、分支保护、看板字段
- 关闭不是你负责的 issue（除非人类明确要求，并在评论里注明）
- 在任何地方写入：密钥、令牌、客户数据、其他客户或其他项目的信息、**公司内部链接**（如 `go/` 短链、内部文档地址）——客户的工程师能看到这里的所有内容
- 编造数字、run-ID、issue 号、文件路径。不确定就去查，查不到就写「未确认」
```

每一条都对应一个真实的风险：标签体系被打乱、仓库误公开、权限被改、别人的问题被误关、内部信息泄露给客户、假数字进了报告。

### 第 10 节「不署名」

```markdown
## 10. 不署名

你用的是运行你的那个人的 GitHub 账号，GitHub 记下的作者就是他，他对内容负责。**不要**在提交、PR、issue、评论、RFC 里注明是 AI 写的：
不加 `Assisted-by`、`Co-Authored-By: <AI>`，不写「由 <工具> 起草」「— <工具> 代 @某人」。

- 账号主人没说过的承诺、表态、诉求，不要用他的账号写出去；拿不准先问他
```

很多 AI 编码工具默认会在提交里加 `Co-Authored-By`。这一节明确覆盖这个默认行为。

## 13.5 规则的变更：AGENTS.md 先改，守则跟着改

- 两份冲突时**以 `AGENTS.md` 为准**，然后回去修守则
- 改 `AGENTS.md` 走 `wiki` 的 PR（规则变更的完整链路见第 8 章 8.8）
- 合并后跑同步脚本

**规矩写给 bot 的推论**：当你（作为人）发现某条规矩没被遵守，先看 `AGENTS.md` 里有没有写、写得够不够具体。
原项目有一次发现 issue 评论里总有「已分给某某跟进」这种话，规矩里虽然写了「不写过程寒暄」，但「分派」显然没被当成寒暄。
于是在第 6 节单独加了一条，把「已接手」「分给某某跟进」「已打标签 / 已进看板 / 状态改成 X」「上游另外跟进」逐个列出来。

**能列举的就列举，不要指望 AI 从一个抽象词推出所有情况。**

## 13.6 同步：`sync-agents.sh`

`wiki/AGENTS.md` 合并进 `main` 之后，跑：

```bash
bash scripts/sync-agents.sh northpeak/wiki#<关联 issue 号>
```

它对每个目标仓库：

1. 取目标分支上的 `AGENTS.md`，和 `wiki` 的逐字节比较，一致就跳过（输出「已一致」）
2. **两个 issue 仓**：同步 `AGENTS.md` 算记录类改动，**直接推 `main`**，提交信息带 `Refs <issue>`
3. **其他仓库**：建分支 `chore/sync-agents-<wiki 短 sha>-<目标分支>`，开一个同步 PR（四栏模板都填好，偏差栏写「无」）

目标列表写在脚本顶部，**一个仓库可以有多个目标分支**（比如 `maxtext:main maxtext:modelx`——开发分支也要有最新的 `AGENTS.md`，因为客户在开发分支上工作）：

```bash
TARGETS="numerics-kit:main maxtext:main maxtext:modelx project-management:main project-management-infra:main gke-component-a:master ..."
DIRECT="project-management project-management-infra"
```

**新仓库建好后加进 `TARGETS`。** 默认分支是 `master` 的要写对。

**不在同步范围内的仓库**：已归档的仓库（只读，推不进去）；以及有自己特殊规矩的仓库——原项目的旧 `repro` 仓库里的 `AGENTS.md` 只是一句「指向 wiki 最新版」的说明加上本仓库特有的一节，不参与同步。

目标仓库还没有 `AGENTS.md` 时（新仓库），脚本要能处理「文件不存在」：取 sha 失败时不带 sha 参数直接创建。完整脚本见 [`appendix/scripts/sync-agents.sh`](../appendix/scripts/sync-agents.sh)。

## 13.7 仓库特有的规矩放哪

少数仓库有自己的规矩（比如 `repro/` 的 `card.yaml` 字段、代码仓的冒烟命令）。**不要写进各仓库的 `AGENTS.md`**（会被同步覆盖），而是：

- 写进那个仓库（或目录）的 `README.md` 或 `FORK.md`
- `AGENTS.md` 里一句话指过去：「上游项目的私有副本：分支和同步规矩以仓库根目录的 `FORK.md` 为准」

## 13.8 让客户的 AI 助手也守规矩

客户的工程师也用 AI 助手。他们的助手读到的是同一份 `AGENTS.md`，所以客户的助手提的 issue、PR 也会按模板、打对标签。

`AGENTS.md` 第 3 节专门有一段写给「客户本人或替客户工作的助手」：代码改动在哪个分支、放不进 issue 的材料放哪、哪些可以直接推。
写的时候要站在客户的角度：**越少规定越好**——不规定分支名，不要求 PR，不要求 README。

## 13.9 在 AI 助手的个人记忆里写什么

厂商工程师自己的 AI 助手（有长期记忆的那种）在这个 org 里干活时，除了读 `AGENTS.md`，还会积累一些**不该写进 `AGENTS.md`** 的东西：

- GitHub 账号和真人的对照（第 3 章 3.10，属于客户数据）
- 客户各方向的接口人
- 内部的 bug 系统、内部文档在哪

这些放在厂商一侧（AI 助手的私有记忆、厂商内部文档），**永远不进 org**。
