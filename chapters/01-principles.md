# 第 1 章 设计原则

后面所有章节的规则都从这十条原则推出来。规则记不住没关系，碰到书里没写的情况，回到这一章推一遍。

## 1. 过程记录本身就是交付物

客户最终拿到的不只是代码和一个数字，还有「这个数字是怎么来的」。
三个月后有人问「这个 loss 为什么和 GPU 差 0.3%」「当初为什么关掉这个开关」，答案必须能点开一条链接看到，
而不是去问某个人还记不记得。

推论：

- **聊天里讨论出的结论，当天回写到对应 issue。** 没写进 issue 的结论等于没有
- **外部链接会过期。** 报告链接可以贴，但结论、表格、关键图必须抄进 issue 评论
- **每次有结论追加一条评论，不改旧评论。** 后来推翻了也是新开一条说明。改掉旧评论就丢了「当时为什么那么想」

## 2. 不遵守还能往下推的规则，不设

这是挑规则的判据。一条规则如果不遵守也不影响手上的活，它迟早没人守，然后开始产出假记录：
字段是空的、状态是错的、文档是旧的。假记录比没有记录更糟，因为有人会信它。

所以每条规则只能是这三种之一：

| 类型 | 例子 |
|---|---|
| **交给机器执行** | issue 模板自动打 type 标签；看板规则自动把关闭的 issue 设为 Done |
| **卡在必经之路上** | 合并前的检查：PR 正文没有关联 issue、没有偏差栏就不合并。原项目早期由 CI 检查；停用 CI 后改为合并前本地自查（第 14 章），这一条因此变弱——升级付费档后应恢复成强制检查 |
| **由少数固定的人执行** | 加人只有 Owner 能做，Owner 按团队加，团队成员列表就是记录 |

做不到这三种的规则，不设。比如「每天更新 issue 状态」——没有机器能执行它，也卡不住任何东西，就不要写。

## 3. 状态靠规则改，不靠人点

看板的状态如果靠人手动拖，一周之后就和现实对不上了。所以：

- 看板自带的自动规则全部打开：issue 关闭 → Done，PR 合并 → Done，PR 关联到 issue → In Progress
- 人只改三个状态：开始写设计文档（Design Pending）、设计文档合并（Ready to Develop）、被外部卡住（Blocked）
- **不要为了「看起来有进展」改状态**
- 只建会被规则自动填、或每周真有人看的字段。用不上的字段别建，建了就会产出假数据

## 4. 会改变事实的动作只用确定性规则；LLM 只写给人看的文字

自动化分两类，边界不能混：

- **改变事实的动作**（改状态、指派、判定完成、合并）：只用确定性的规则和脚本
- **LLM 能做的**：写日报、周报、摘要、拆分建议——都是给人看的文字，由人决定采不采纳

AI 编码助手在 org 里写 issue、写 PR、写代码，是用某个人的账号、在那个人的指示下做的；
它不能自己决定关 issue、合并 PR、改看板状态（第 13 章）。

## 5. 一个人对一切负责，AI 不署名

AI 助手用运行它的那个人的 GitHub 账号，不单独开账号，不进任何团队。GitHub 记下的作者就是那个人，他对内容负责。

**不在提交、PR、issue、评论里注明是 AI 写的**：不加 `Co-Authored-By: <AI>`，不写「由某某工具起草」。

原因：署名是为了追责。账号主人已经是作者和负责人了，再加 AI 署名只会模糊责任——
读者会以为「这是 AI 写的，可能不准」，或者「这不是他本人的意见」。账号主人要么为内容负责，要么别发出去。

推论：**账号主人没说过的承诺、表态、诉求，不要用他的账号写出去**；账号主人没拍板的后续动作（比如给上游提 issue）不写成计划。

## 6. 按受众分仓库，不按内容类型分

GitHub 上权限、订阅（watch）、issue 模板、新建入口都以**仓库**为单位，标签只能用来筛选。
所以：

- 受众不同、分诊的人不同，就该分仓库
- 受众相同，就不要拆：内容类型不同（文档、配方、复现脚本）不是拆仓库的理由

原项目一开始是按内容类型分的（`library` 放文档、`recipes` 放配方、`repro` 放复现），后来发现客户的 GKE 组不该看训练的东西，
按受众一拆就会变成六个仓库，于是全部并回按受众划分的两个 issue 仓库。第 2 章和第 16 章细讲。

## 7. 规矩主要写给 AI 助手

一个工程师一天提的 issue、写的 PR，很多是 AI 助手代写的。规矩写给 AI 有三个好处：

- **AI 照字面执行**，比人守规矩。写清楚了，它每次都对
- **逼着规矩写具体**。「issue 要写清楚」对 AI 没用；「正文用 `### 字段名` 作小标题，按这个顺序写」才有用。写具体了，人也受益
- **人只要说一句话**：「先读 AGENTS.md，再按里面的规矩来」

所以规则有两份：

| 文件 | 给谁 | 写什么 |
|---|---|---|
| `AGENTS.md` | AI 助手 | 怎么做：命令式、带命令、带 ID、带枚举值 |
| 守则文档 | 人 | 为什么：每条规则的原因 |

两份冲突时以 `AGENTS.md` 为准，然后回去修守则。

## 8. 客户看得到的地方，什么都可能被看到

org 里的一切，迟早有人会误授权、误转发。所以：

- 客户能看到的仓库里，不写密钥、令牌、客户数据、**其他客户或其他项目的信息、厂商内部链接**（内部短链、内部文档地址）
- org 名、仓库名对外可见：**不用客户名，不用未公开的产品代号**
- 能不放进 org 的厂商内部材料就不放。设一个「厂商专属仓库」的口子，就会有人往里放不该放的东西，然后某天它被误授权

## 9. 默认平铺，不建层级

一个问题一个 issue，默认平铺，不按阶段、按月、按模块归堆。只在两种情况开总表（第 6 章）。

原因：层级要维护。阶段总表开出来第一周很漂亮，第三周就没人往里挂新 issue 了。
而且范围太大的总表等于没分——「十月份的所有问题」不是一个可以跟踪的东西。

## 10. 免费档能做到的就够用

原项目始终在 GitHub 免费档。免费档的私有仓库**没有分支保护**，也就是说：

- 不能强制「合并前至少 1 人批准」
- 不能强制「检查不过不能合并」
- 有 Write 的人可以直接推 `main`

这些都靠规矩补：评审现阶段不强制、检查靠合并前自查、误操作靠提交历史回退。
等人多起来、真需要强制时再升级。**不要为了「流程完整」一开始就上付费档**：先跑起来，看哪条规矩真的被绕过了，再花钱补那一条。

---

## 这套做法不适合什么项目

- **双方只有两三个人**：一个共享文档就够了，这套规则的开销大于收益
- **客户不愿意在 GitHub 上协作**（安全政策、习惯）：规则可以搬到别的平台，但第 2–5 章的具体做法要重写
- **项目只持续两三周**：建 org、教会大家用的时间就要一周
- **主要工作是商务和交付治理**（合同、排期、资源申请）：这些不该放进工程 org。原项目明确把它们排除在外，遇到相关请求回复说明范围并转到别处
