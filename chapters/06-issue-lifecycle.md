# 第 6 章 issue 的一辈子

**一个问题一个 issue，一个 issue 记全这个问题的一辈子**：提出、分诊、排查、转移、等待、关闭。

## 6.1 没有 issue 不写代码

**规则：开工前先确认有对应的 issue。没有就先建。**

开工前的三步（写进 `AGENTS.md` 第 0 节）：

1. 确认有对应的 issue。没有就建
2. 读 issue 正文、子任务、关联 RFC 和最新的评论。**以最新评论为准**（正文可能已被后续评论推翻）
3. 如果是大任务（`size/L`），确认 RFC 已合并；没合并只能写 RFC，不能写实现

**为什么**：没有 issue 的代码改动，三个月后没人知道它为什么存在。PR 必须关联 issue（第 7 章），
所以先写代码后补 issue 的人会发现补的 issue 只有一句话，等于没写。

## 6.2 提出：放在哪个仓库

| 是什么 | 放哪 |
|---|---|
| 规矩、流程、权限、org 设置的改动（哪怕涉及多个仓库） | `wiki` |
| 项目上的事，作业里面的（模型、框架、精度、性能、镜像依赖……）以及兜底 | `project-management` |
| 项目上的事，集群和节点层面的（切片、调度、节点池、存储挂载、网络、配额……） | `project-management-infra` |

**客户在自己看得到的仓库提就行，不用先判断属于哪边。** GKE 组只看得到 infra 仓，他们提的一切都在 infra；
训练组两边都能看，拿不准的**建在现象出现的那一边**——作业跑挂了就在训练仓，节点起不来就在 infra 仓。分诊时再挪。

## 6.3 提出：客户写的 issue

客户提 issue 时只需要做一件事：**选对模板，用自己的话写清「问题描述」**。其余栏是建议，不填也行。

厂商工程师替客户建 issue 时（比如客户在聊天群里提了问题），规则更严：

- **正文放客户原话**：引用块，一字不改；原始截图跟在后面
- **截图存到 issue 所在仓库的 `assets/issues/<阶段>/`**，正文里用完整地址引用：`https://github.com/<org>/<repo>/blob/main/assets/issues/<阶段>/<文件>?raw=true`。issue 正文**不解析相对路径**。存进仓库而不只拖进输入框，是为了不依赖 GitHub 的图片 CDN，仓库 clone 下来图还在。`<阶段>` 是项目阶段名（如 `poc`、`phase2`），建站时定好写进 `AGENTS.md`
- **原话没写完或有歧义：写出你的理解，并请客户确认。不要替客户补全问题**
- 然后写环境和「怎么算完成」

**为什么一字不改**：客户的原话是需求的原始记录。改写后，三个月后争论「客户到底要的是什么」时就没有依据了。
你的理解可以写，但写在原话下面、明确标为「我们的理解」。

示例（虚构）：

```markdown
### 问题描述

> 我们在 v5p-128 上跑 ModelX 32 层，开了 cp=4 之后 loss 比 cp=1 高了一截，大概 0.02 左右，
> 跑到 2000 步还没收回来。是不是 cp 的 attention mask 有问题？

![loss 曲线](https://github.com/northpeak/project-management/blob/main/assets/issues/poc/cp-loss-offset-1.png?raw=true)

我们的理解：同一配置下只改 context parallelism（1 → 4），loss 在 2000 步内稳定高约 0.02，
客户怀疑 cp 切分后的 attention mask。请 @carol-c 确认：两次运行的数据顺序、随机种子是否相同？

### 跟哪块有关

不知道 / 都不是
```

## 6.4 提出：不要求客户补填

**规则：模板里只有「问题描述」是必填，不要要求客户补填其他栏。**

缺的运行条件（代码与版本、硬件与规模、模型数据与并行、命令、run-ID）**由我们查清后写进第一条评论**；
查不到的才在评论里问客户。

**客户选错了模板或类型，直接改标签，不要让客户重提。**

**为什么**：每一次「请补充 X 信息」都是一次来回，客户要切换上下文、找信息、回复。
厂商工程师多数时候自己就能查到（看客户的作业日志、看集群事件），自己查比问快。
让客户觉得「提 issue 很麻烦」，他们就会回到聊天群。

## 6.5 分诊

分诊就是处理看板上 Status = Triage 的那一列。原项目没有写死谁来分诊，由厂商一侧的技术负责人和熟悉各领域的工程师顺手做；人多了建议排一个轮值（第 18 章）。分诊要做的：

| 做什么 | 怎么做 |
|---|---|
| 确认在对的仓库 | 不对就转移（6.6） |
| 确认 type 标签对 | 不对直接改 |
| 加进看板（命令行建的 issue） | `board.sh add <URL> S` |
| 指定负责人 | 设 assignee |
| 判断大小 | `size/S` 或 `size/L` |
| 判断优先级 | `P0` / `P1` / `P2`，拿不准不打 |
| 补运行条件 | 查清后写第一条评论 |

**认领 = 设 assignee**，不另设状态，也不评论「我来看」。

### 固定路由

有些类别的 issue 总是由同一个人或团队跟，写成固定路由，分诊时直接设 assignee：

> 原项目的例子：MaxText 相关、需要上游 MaxText 团队跟进的 issue，assignee 设为上游团队的对接人，那个团队会一起看。

固定路由写进 `AGENTS.md` 第 2 节，AI 助手分诊时照做。路由变了就改 `AGENTS.md`。

### 新 issue 先给一个人统一路由

项目初期或一次会议后集中产生一批 issue 时，可以**先全部分给一个熟悉全局的人**，由他再分给具体的人。
原项目在一次会后建了十几条 issue，初始 assignee 都给了厂商一侧的技术负责人，他在一两天内再路由。
这比建 issue 的人凭印象分给各个人更准。

### 不要建太多 issue

一次会议或一份客户问题清单里可能有五十个问题。**只为讨论过的、重要的问题建 issue**，不要因为它出现在清单上就建。
五十条 issue 一次性出现在看板上，没人会认真看任何一条。剩下的先留在会议纪要里（第 11 章），真成为问题了再建。

## 6.6 转移：放错了仓库怎么办

**拿不准就建在现象出现的那一边。分诊时发现属于另一边，不要让客户重提。** 按谁参与过、往哪边挪，分四种情况：

| 情况 | 做法 | 为什么 |
|---|---|---|
| 厂商同事提的、没有客户参与 | **转移**：`gh issue transfer <号> <org>/<另一个仓库> -R <org>/<当前仓库>` | 没有可见性问题 |
| 客户参与过，从训练仓 → infra 仓 | **转移**（合作方参与过的除外） | 训练组两边都看得到，转过去报告人还能看 |
| 客户参与过，从 infra 仓 → 训练仓 | **不转移**。在训练仓新开一条，正文链回原 issue，原 issue 评论里链过去 | GKE 组、网络组看不到训练仓，转过去报告人就看不到自己的 issue 了 |
| 合作方参与过，从训练仓 → infra 仓 | **不转移**，同上一行做法 | 合作方看不到 infra 仓 |

不转移时：**原 issue 留给报告人，另一边的结论当天同步成原 issue 的评论，两条一起关。**

转移要求两边仓库都有 Write，所以只有厂商同事能做（厂商同事两边都是 Maintain）。

### 转移后核对两件事

1. **标签**：目标仓库没有的同名标签会丢。按目标仓库的标签补齐 `type/*` 和 `area/*`：
   - `type/accuracy` 在 infra 没有，改打 `type/bug`
   - `area/env` 两边含义不同（训练仓是「环境、版本、镜像、依赖」，infra 仓是「配额与容量」），要重判
2. **看板**：条目还在、字段没变。丢了用 `board.sh add` 补回

GitHub 文档没有写看板条目会不会随转移保留。社区报告说同一 org 内条目和状态通常保留，但看板相关的时间线记录会消失，也有人报过字段丢失。
**转移前记下 Status 和 Size，转移后逐条核。**

旧链接会自动跳转到新地址（REST API 对旧地址返回 301），所以别处贴的老链接不会断。

## 6.7 一个问题只在一个地方排查

**规则：一个问题的排查过程只记在一个仓库。根因在哪边就由哪边持有；另一边的 issue（不转移时留下的那条，或需要跟踪时开的那条）只链过去、同步结论，不重复记录过程。**

例：训练组报「作业每隔几小时挂一次」（训练仓），查下来是节点维修事件导致的（infra 仓的事）。

- 在 infra 仓开一条「排查节点维修导致作业中断」，排查过程全部记在这里
- 训练仓那条评论链过去：「根因在 `northpeak/project-management-infra#14`，那边有结论会同步到这里」
- infra 那边出结论后，**结论本身**（不只是链接）写成训练仓那条的评论
- 两条一起关

**为什么不能只贴链接**：训练仓的读者里有合作方，打不开 infra 仓。要他们看的结论，写进他们看得到的那条 issue。

## 6.8 排查中：评论怎么写

**规则：每次有结论追加一条评论，不改旧评论。** 后来推翻了也是新开一条说明。

一条好的评论：

- 写日期（评论时间戳之外，如果是在说某次运行，写运行的日期）
- 写结论，然后是证据：数据表、图、命令、run-ID
- 写需要客户补充的信息（如果有）

**外部链接会过期**。报告链接可以贴，但结论、表格、关键图必须抄进评论，图片存到 `assets/issues/<阶段>/`。

### 评论只写事实和结论

**不写过程寒暄和流程信息。** 以下都不写：

| 不写 | 为什么 |
|---|---|
| 「已接手」「我来看一下」 | assignee 已经说明了 |
| 「分给某某跟进」「@某某 请跟进」 | 改 assignee 就行 |
| 「已打标签」「已加入看板」「状态改成 Blocked」 | 标签、看板自己就说明了 |
| 「上游另外跟进」 | 要么贴上游 issue 链接，要么不写 |
| 「感谢反馈」「收到」 | 零信息量 |

**为什么**：issue 是要被很多人反复读的。三个月后有人翻这条 issue，每一条流程评论都是噪音。
assignee、标签、看板状态的变化 GitHub 都会记在时间线上，不需要再用评论复述一遍。

### 账号主人没拍板的不写成计划

「我们会给上游提 PR」「下周给出修复」——账号主人没拍板的后续动作，不写成计划。
写了就是承诺，客户会按这个时间等。这条对 AI 助手尤其重要：它很容易顺手写一句「接下来我们会……」。

### 改别人的正文前先评论

修改别人的 issue 正文之前，先评论说明要改什么。正文是报告人的，悄悄改掉会让人困惑。

## 6.9 等待：Blocked

被外部卡住时（等客户提供信息、等上游修复、等资源）：

1. 看板设 Blocked：`board.sh status <URL> "Blocked"`
2. **同时**评论卡在哪、等谁

**修复给出但客户还没验证：不关 issue，设 Blocked，评论在等什么。**
修复「给出」和问题「解决」是两回事。客户在自己的环境里验证通过，才算解决。

## 6.10 关闭

一个 issue 只有同时满足以下几条才算完成：

- issue 里「怎么算完成」/「验收标准」的每一条都已验证，**在 issue 里附了证据**（命令输出或 run-ID）
- 相关 PR 已合并，偏差已记录（第 7 章）
- 文档（README、RFC、wiki）已同步
- issue 已关闭（合并 PR 时自动关闭；合进非默认分支的要手动关，第 7 章）

**不关不是你负责的 issue**（除非人类明确要求，并在评论里注明）。

问询类（`type/question`）的 issue：答案写成评论，报告人确认后关。报告人长期不回怎么办，原项目没有定规矩；建议负责人隔一周关掉，评论写「如有后续请重开」，并把这条写进你的 `AGENTS.md`。

## 6.11 总表（tracker）：默认不开

**一个问题一个 issue，默认平铺，不分堆。** 只在两种情况开总表（打 `tracker` 标签，用 GitHub 的 sub-issue 把相关 issue 挂上去）：

1. **几个 issue 确实是同一个问题的不同方面**。例如都是数据并行和 FSDP 之间的 loss 对齐，从不同的模型、不同的规模报上来。堆要小，只放真正相关的
2. **一个大任务要拆给不同的人**。大任务本身就是总表，拆出的子任务挂在下面

**不要**：

- 按阶段、按月、按仓库开总表——范围太大等于没分
- 往下套第三层
- **拿不准能不能归堆，就不归**

总表正文写这几个问题的**共同背景**，不重复子任务的内容。

## 6.12 上游的 bug

问题根因在上游开源项目（JAX、XLA、Kubernetes 组件……）时：

- 在上游仓库另提 issue（如果账号主人同意，见 6.8「没拍板的不写成计划」）
- 这边的 issue 贴上游链接跟踪，结论同步回来
- 有临时补丁的，补丁打在我们的私有副本上（第 9 章），issue 里写清补丁在哪个分支、哪个提交
- 不打特殊标签

## 6.13 两个仓库的编号互相独立

重申第 2 章：**跨仓库引用写全名**。在 issue 评论里写 `northpeak/project-management-infra#14`，不写 `#14`。

## 6.14 一条完整 issue 的样子（虚构）

```
northpeak/project-management#31  修复 cp=4 时 loss 偏高约 0.02
labels: type/accuracy  size/S  area/maxtext  P1
assignee: bob-g

正文
  ### 问题描述
  > （客户原话）
  （截图）
  我们的理解：……请 @carol-c 确认……

评论 1  bob-g  10-21
  运行条件已补齐：northpeak/maxtext @ modelx @ 1a2b3c4，jax 0.11.1 / libtpu 0.0.46，
  v5p-128（4x4x8），ModelX 32 层，C4，GBS 256，seq 8192，FSDP 16 × CP 4 × DP 2。
  run-ID：cp1-r17、cp4-r17。

评论 2  carol-c  10-21
  确认，两次同一个数据顺序和种子。

评论 3  bob-g  10-23
  结论：cp=4 时 load balancing 重排了序列，但 loss mask 没跟着重排，
  每个 batch 约 1.6% 的 padding token 被算进了 loss。
  | 运行 | 2000 步 loss | 和 cp=1 的差 |
  |---|---|---|
  | cp1-r17 | 2.4113 | — |
  | cp4-r17 | 2.4318 | +0.0205 |
  | cp4-fix-r19 | 2.4109 | −0.0004（容差 ±0.002 内） |
  复现：northpeak/project-management/repro/issues/31-cp-loss-offset/（commit permalink）
  修复：northpeak/maxtext#58

（PR #58 合并进 modelx 分支；modelx 不是默认分支，不会自动关）

评论 4  bob-g  10-24
  已合并 northpeak/maxtext#58 到 modelx @ 9a1c2e0。等客户在 v5p-256 上验证。
  → 看板设 Blocked

评论 5  carol-c  10-28
  v5p-256 上 cp=4 和 cp=1 对齐了，差 0.0003。

（bob-g 关闭 issue，评论「由 northpeak/maxtext#58 完成」）
```

注意这条 issue 里**没有**的东西：没有「我来看一下」，没有「已打标签」，没有「@xxx 请跟进」，没有「下周给修复」。
