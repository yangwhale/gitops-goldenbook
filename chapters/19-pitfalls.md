# 第 19 章 踩过的坑

按「在哪踩到」分组。每条：现象、原因、怎么办。大多数已经写进前面各章的规则里，这里集中列出，复刻时逐条过一遍。

## 19.1 GitHub 本身的反直觉行为

| 现象 | 原因 | 怎么办 |
|---|---|---|
| PR 写了 `Closes`，合并后 issue 没关、看板停在 In Progress | PR 合进的**不是默认分支**，GitHub 只在合进默认分支时按 `Closes` 关 issue | 合并后手动关：`gh issue close <URL> --comment "由 <PR> 完成"`（第 7 章） |
| 在代码仓的 PR 里写 `Closes #3`，关错了或没关 | 裸 `#3` 按**当前仓库**解析 | 一律写全名 `<org>/<repo>#3`（第 2 章 2.10） |
| 迁移过来的旧提交在新仓库不相干的 issue 时间线上留下引用 | 提交信息里的裸 `#N` 被新仓库按自己的编号解析 | 迁移时用 `filter-repo --message-callback` 改写成全名（第 16 章） |
| `gh pr edit` 报 GraphQL 权限错误 | 它走 GraphQL，要令牌有 `read:org` | 用 REST：`gh api -X PATCH repos/<org>/<repo>/pulls/<号> -F body=@body.md`（第 7 章） |
| issue 模板从新建页上消失了 | YAML 语法对但表单字段不合法，GitHub **只在页面上提示** | 推前 `yaml.safe_load`，推后逐个点开模板（第 4 章） |
| 新仓库删了默认标签，后来又冒出来 | 默认标签在建仓库后**异步**生成 | 最后按实际列表删表外标签（`setup-labels.sh`，附录 C） |
| 转移 issue 后标签丢了 | 目标仓库没有的同名标签不会带过去 | 转移后按目标仓库补 `type/*`、`area/*`（第 6 章 6.6） |
| 转移 issue 后看板字段可能丢 | GitHub 文档没写会不会保留；社区有字段丢失的报告 | 转移前记下 Status、Size，转移后核 |
| 公开项目 fork 不出私有仓库 | GitHub 上公开仓库的 fork 只能是公开的 | 建私有仓库，`push --mirror`，写 `FORK.md`（第 9 章） |
| 免费档里成员能建公开仓库，关不掉 | 免费档只能全开或全关「建仓库」 | 靠规矩：「建仓库一律 Private」，误建立刻告诉管理员；季度对账查（第 18 章） |
| 免费档私有仓库设不了分支保护 | 分支保护对私有仓需要 Team 档 | 评审不强制、检查靠本地自查；接受强推风险（第 3、14 章） |
| 强推覆盖了 `main`，想找回 | 只能靠某个成员的本地克隆，或 `repos/<org>/<repo>/events` 里的 SHA（GitHub 现行文档：只保留 30 天、最多 300 条；原项目 RFC 里写的 90 天是旧说法） | 能升级 Team 档就开分支保护；否则写明接受这个风险（第 16 章 16.3） |
| 看板视图筛选 `repo:<org>/project-management` 里混进了 infra 仓的条目（原项目的视图带了排除） | 文档没说 `repo:` 是否前缀匹配 | 加 `-repo:<org>/project-management-infra` 排除，建完数一下条目（第 5 章） |
| 免费档只能开 1 条 Auto-add 规则 | 每条只能盯一个仓库 | 两个 issue 仓时不用它，`board.sh add` 必做（第 5 章） |
| 只有 Owner 能邀请新成员 | 免费档的权限设计 | Owner 数量按「加人请求能不能当天处理」定（第 3 章 3.2） |
| 邀请过期 | 邀请 7 天有效 | 定期查 `orgs/<org>/invitations`，过期重发 |

## 19.2 看板

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 停用 Actions 后，各仓库的 `FORK.md`、README、守则里还写着「pr-check 会检查」「检查通过自动合并」 | 改规则只改了 `AGENTS.md` | 改规则后全 org grep 一遍旧说法（第 16 章 16.5 的「同时改四处」） |
| `sync-agents.sh` 开出的同步 PR 在几个代码仓里没人合，`AGENTS.md` 不一致 | 同步脚本只开 PR，不合并 | 跑完脚本当天把 PR 合掉；季度对账再跑一次脚本，应全部「已一致」 |
| 一部分开着的 issue 不在看板上 | 网页上建的 issue 不会自动进看板；客户自己提的没人加 | 分诊时加；季度对账用第 18 章的命令查。原项目某次对账：开着的 issue 里约三成不在看板上，大部分在 infra 仓 |
| 看板状态和 issue 对不上 | 有人手动拖到 Done | 规矩：Done 只能由 issue 关闭触发（第 5 章） |
| Blocked 一堆，没人知道在等什么 | 只改状态不评论 | 规矩：Blocked 必须同时评论（第 5 章） |

## 19.3 AI 助手

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 提交里出现 `Co-Authored-By: <AI>` | 很多 AI 编码工具默认会加 | `AGENTS.md` 第 10 节明确禁止（第 13 章） |
| 评论里写「已分给某某跟进」「已打标签」 | AI 不认为这是「寒暄」 | 把不写的话**逐项列举**（第 13 章 13.5） |
| 编了一个不存在的标签或看板状态 | 枚举值没写全 | `AGENTS.md` 里逐字列出所有枚举值（第 13 章） |
| 命令行建的 issue 和网页上的格式不一样 | AI 不知道表单生成的正文格式 | 规则：`### 字段名` 按模板顺序写（第 4 章 4.4） |
| 下拉选项被拆错（选项里本身有斜杠） | 选项没有边界 | 每个选项单独放在反引号里，写明「每个反引号里是一个完整选项」 |
| AI 替账号主人许诺「下周给修复」 | 顺手写的 | 规则：没拍板的后续动作不写成计划（第 6 章 6.8） |
| AI 在 `maxtext` 里干活，不知道规矩 | AI 只读当前工作目录 | 每个仓库都放 `AGENTS.md`，`sync-agents.sh` 同步（第 13 章） |
| 同步脚本在新仓库上失败 | 新仓库还没有 `AGENTS.md`，取 sha 报错 | 取 sha 时 `|| true`，有 sha 才带（第 14 章） |
| AI 写进 issue 的数字查不到来源 | 规则没要求 | `AGENTS.md` 第 5 节：没有来源的数字不写；不确定写「未确认」 |

## 19.4 权限与可见性

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 训练组提不了集群问题 | 可见性做成了对称隔离 | 先画可见性矩阵，问「这个组会不会碰到另一个方向的问题」（第 16 章 16.2） |
| GKE 组点 issue 里的链接 404 | 链接指向他们看不到的仓库 | 结论写进他们看得到的 issue，不只贴链接（第 2 章 2.10） |
| `config.yml` 里的链接 404 | 同上 | infra 仓不放指向训练仓的链接；训练仓的链接说明里写「打不开就在本仓库提」（第 4 章 4.3） |
| 子团队名叫 `customer-gke` | 加了父团队前缀 | GitHub 显示本来就带层级，不加前缀 |
| 某人能看什么查不清 | 一人多团队、或用了单仓直授 | 一人一团队，不用单仓直授（第 3 章） |
| 成员身份被看到 | 有人把 org 成员身份设成了公开 | 默认隐藏，规矩里写明不要改 |

## 19.5 仓库与迁移

| 现象 | 原因 | 怎么办 |
|---|---|---|
| org 里有几个空仓库 | 导入时上游本来就是空的 | 有公开版的导公开版，空的不建（第 9 章 9.5） |
| 跟随副本的自动同步把内部链接带进了客户能看的仓库 | 上游提交说明里有内部 bug 链接 | 自动同步过滤内部链接，命中就不推、报人工（第 9 章 9.4） |
| rebase 后丢了上游新加的代码 | 冲突时整文件取了一边 | 逐文件核对；CPU 冒烟能抓到（第 9 章） |
| 迁移后历史没了 | 迁移 PR 用了 squash | 必须 merge commit；合并前临时关 squash 和 rebase（第 16 章） |
| issue 评论里的老链接全断了 | 迁移后删了旧仓库 | 归档，不删除 |
| 客户 clone 下来 PDF 打不开（预先排除的，原项目没真踩到） | 用 Git LFS 存 PDF，客户没装 git-lfs，拿到的是一行指针 | PDF 直接提交，单个 ≤ 20 MB（第 10 章） |
| 开发分支名带代数，下一代的代码没地方放 | 分支名带了代号 | 开发分支不带代号，旧的冻结成快照（第 9 章） |

## 19.6 流程

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 会后一次建了五十条 issue，没人看 | 把客户的问题清单原样搬进来 | 只建讨论过的、重要的（第 6 章 6.5） |
| 「客户到底要的是什么」吵不清 | 替客户改写了原话 | 正文放原话，一字不改；理解另写（第 6 章 6.3） |
| 客户回到聊天群提问 | 提 issue 门槛太高（必填栏太多、总要求补信息） | 只有第一栏必填；缺的信息我们查（第 4、6 章） |
| 修复「给出」了就关 issue，客户那边还是不行 | 把给出当成了解决 | 客户验证前设 Blocked，不关（第 6 章 6.9） |
| 三个月后 issue 上写的方案和代码对不上 | 实现改了没回头记 | PR 偏差栏必填；偏差大时回去改 issue / RFC（第 7 章） |
| 阶段总表没人维护 | 范围太大 | 默认平铺，总表只在两种情况开（第 6 章 6.11） |
| 会议转写的纪要里 A 的话记成了 B 说的 | 自动转写的说话人标注错 | 人工校对，涉及结论和承诺的逐句核（第 11 章 11.8） |
| 规则改了，有的仓库还按旧的做 | `AGENTS.md` 没同步，或守则、主页没跟着改 | 改规则同时改四处，跑 `sync-agents.sh`（第 16 章 16.5） |
| GitHub Actions 分钟数用完 | 每次推送都跑 CI | 只跑秒级检查，或干脆停用（第 14 章） |
| 给客户的说明越写越长 | 想把所有细节都告诉客户 | 只说「去哪提、拿不准怎么办」，其他的点进主页自然看到（第 15 章第 16 步） |

## 19.7 令牌和工具

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 邀请成员、改成员角色报 403 | 令牌没有 `admin:org` | `gh auth refresh -s admin:org` |
| 删测试仓库报 403 | 令牌没有 `delete_repo` | `gh auth refresh -s delete_repo` |
| 看板命令报权限错 | 令牌没有 `project` | `gh auth refresh -s project` |
| 提交信息里的反引号、`$` 被 shell 吃掉 | 正文写在 `-m` 里 | `git commit -F <文件>`（第 7 章） |
