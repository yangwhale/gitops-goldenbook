# 前言：这本书解决什么问题

## 一个常见的场景

一个联合工程项目开始了。厂商这边四五个工程师，客户那边十几个，分成训练组、集群组、网络组。
头两周，所有问题都在一个几百人的聊天群里：

- 客户贴一张报错截图，三个人同时回复，各自给了不同的建议
- 一周后有人问「上次那个 NaN 最后怎么解决的」，没人找得到那段聊天
- 一个性能数字在周报里出现了三次，三次的值不一样，没人说得清是哪次运行测的
- 一个方案在会上定了，两周后实现出来的跟会上说的不一样，没人记得是什么时候改的、为什么改
- 客户的 GKE 组被训练组的消息刷屏，干脆不看群了

这些问题本身都不难。难的是它们**每天都在发生**，靠人的自觉去避免，坚持不了两周。

## 这本书的做法

把协作搬进一个 GitHub org，再用一套规则把它管起来：

- **问题进 issue**：一个问题一个 issue，提问、截图、每次分析、结论都按时间记在这一条上
- **代码进 PR**：每个 PR 关联一个 issue，正文必须写「和原计划的偏差」
- **方案进 RFC**：大任务先写设计文档，合并了才开发；规则本身的改动也走 RFC
- **进度看看板**：状态尽量让规则自动改，人只改少数几个
- **规则写两份**：给人看的讲「为什么」，给 AI 助手看的（`AGENTS.md`）只讲「怎么做」，命令式、带命令和 ID

最后一条是这套做法和普通「项目管理规范」最大的不同。现在一个工程师一天提的 issue、写的 PR，
很大一部分是 AI 编码助手代写的。**规则主要写给 AI 助手**：它们会照字面执行，执行得比人严格。
规则写得够具体，AI 助手就是最守规矩的那个同事。

## 这本书和别的规范有什么不同

**每条规则都按一个判据挑过：不遵守它，手上的活还能不能往下推？**
能推的规则迟早没人守。所以书里的规则要么交给机器执行（模板、脚本、检查），要么卡在合并这一步上，做不到的就不设。
你会发现这本书里**没有**很多常见的规则，比如「每天更新 issue 状态」「每周写进度报告」——那些靠自觉的规则，在真实项目里都烂掉了。

**每条规则都写了原因。** 原因比规则本身更重要：你的项目情况不同时，知道原因才知道能不能改、怎么改。

**规则改过很多轮，改的过程也记下来了。** 第 16 章讲了几次真实改版：为什么从一个 issue 仓库拆成两个，
为什么又把三个交付物仓库并回去，为什么客户各组的可见性从「全都能看」改成「不对称」。
这些改版能告诉你：哪些地方一开始就该做对，哪些地方可以先简单后补。

## 读这本书需要知道什么

- 会用 GitHub：issue、PR、label、Projects（新版看板）。不熟的先读[附录 F GitHub 速成](../appendix/F-github-primer.md)
- 会用 `gh` 命令行（书里的命令大多是 `gh api`）
- 不需要懂 TPU、GKE 或机器学习。书里的例子用到这些领域的词，但规则本身和领域无关。第 12 章后半和数值有关，不做数值的项目可以跳过

## 约定

- `<org>`：你的 GitHub org 名。书里的示例 org 叫 `northpeak`
- 「厂商」：提供技术支持的一方（原项目里是 Google）；「客户」：接受支持的一方
- 「Google 同事」：原项目的说法，复刻时换成你的厂商工程师。书里引用原规则原文时保留这个说法
- **加粗**的是规则本身；规则后面的段落是原因
- 示例里的 GitHub 账号（`alice-g`、`carol-c` 等）、issue 号、commit 号都是编的；后缀 `-g` 表示厂商一方，`-c` 表示客户一方
